# Enterprise design system developer tooling: Atlassian (ADS), Shopify Polaris, GitHub Primer, Salesforce SLDS

Research date: 2026-10-07. npm metadata (versions, dates, weekly downloads) was pulled live from `registry.npmjs.org` and `api.npmjs.org/downloads` on that date. Download counts cover the week 2026-09-28 to 2026-10-04.

## Q1. What commands and capabilities does each system ship (lint, autofix, migrate/codemod, upgrade, tokens, init, MCP)?

### Takeaway
None of the four ships a single "design-system CLI" like the proposed Helix CLI. Each spreads its tooling across separate packages:
- an ESLint and/or Stylelint plugin, which is the main enforcement surface;
- a codemod runner, mostly jscodeshift-style, with "Hypermod" at Atlassian;
- since 2025, an MCP server.

Salesforce is the closest to a single CLI. `@salesforce-ux/slds-linter` has `lint`, `lint --fix`, `report` (which writes SARIF) and `emit`, wraps its own ESLint plugin, and is also built into Salesforce Code Analyzer and an MCP "uplift" tool.

- **Styling-standard plugin.** A companion plugin, `@atlaskit/eslint-plugin-ui-styling-standard` (created 2024-01, v3.0.1 on 2026-10-02), enforces Atlassian's "UI Styling Standard" — [npm registry](https://registry.npmjs.org/@atlaskit/eslint-plugin-ui-styling-standard); [atlassian.design/llms.txt](https://atlassian.design/llms.txt)

  - `@atlaskit/codemod-cli` (v2.1.4, 2026-09-24) was created "to download and run codemods" for atlassian-frontend packages. Its stated purpose: major upgrades "assisted by codemods, reducing upgrade-pain, improving adoption." — [npm README](https://www.npmjs.com/package/@atlaskit/codemod-cli)

  - `@hypermod/cli`: latest version 0.27.3 (2025-08-10) — [npm registry](https://registry.npmjs.org/@hypermod/cli)
  - The ADS llms.txt lists codemods via `@hypermod/cli`, for example "primitives emotion-to-compiled" and "theme-to-design-tokens" — [atlassian.design/llms.txt](https://atlassian.design/llms.txt)

A migration Figma plugin and an Atlassians-only Chrome extension let you "view progress and toggle between themes in an app during migration" — [npm registry](https://registry.npmjs.org/@atlaskit/tokens); [ADS: Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens)

Created 2025-06-06; v1.10.11 on 2026-10-06; status "Early Access"; about 557 downloads a week — [npm registry](https://registry.npmjs.org/@atlaskit/ads-mcp); [npm README](https://www.npmjs.com/package/@atlaskit/ads-mcp)

### Inferences
- All four rely on ESLint and/or Stylelint as the enforcement layer, with design-system-specific rule names. Autofix is used for mechanical changes (token substitution, deprecated imports and props). Accessibility and component-choice rules are left as warnings or suggestions.
- SLDS's single binary is the closest model for a Helix CLI: `lint` / `lint --fix` / `report` (SARIF) / `emit` wraps an ESLint plugin, and the same engine feeds both an IDE and an MCP orchestration tool. Atlassian's codemod CLI features, `--since-ref` and `--packages pkg@fromVersion`, are good patterns for an "upgrade" command.
- Shopify shows that in 2025–26 a major platform shift (React → web components) was handled with agent skills plus MCP validation rather than new codemods. Polaris's lint and codemod packages have been frozen since March 2025.
- No system targets Angular. All of their codemods are jscodeshift-style for React or CSS. Angular schematics (`ng update`) would be the natural equivalent for @cdx/*, though this is outside the cited sources.

## Q2. How does each system measure or enforce adoption (lint coverage, usage tracking across repos, deprecation tracking)? Is there public impact data?

### Takeaway
- Shopify built adoption *measurement* into the linter itself: Stylelint-Polaris has a "coverage" meta-rule and strict rules about disable comments.
- Salesforce treats the SARIF violation count as the uplift metric, with zero violations meaning "uplifted".
- Atlassian and GitHub enforce through recommended lint configs and deprecation rules, and measure internally. Their public numbers come from engineering blogs rather than published dashboards.
- Primer's agent-assisted sx-prop burn-down is the best public impact dataset found.

### Cited Findings
- **Shopify coverage-by-lint:**
  - Stylelint Polaris rules "help measure the Polaris design system's coverage in the Shopify admin code base" — [Polaris docs (search snippet)](https://polaris-react.shopify.com/tools/stylelint-polaris)
  - `polaris/coverage` reports each violation under a category-scoped rule name (e.g., "Please use a Polaris color token Stylelint(polaris/colors/color-named)"). Each category can attach a documentation URL that is hyperlinked in VS Code diagnostics — package source `index.js` and `plugins/coverage/index.js` v16.0.7, [npm](https://www.npmjs.com/package/@shopify/stylelint-polaris)
  - The shared config sets `reportDescriptionlessDisables: true` and `reportNeedlessDisables: true`. This means every `stylelint-disable` must carry a reason and unused disables are flagged, which makes opt-outs auditable as coverage gaps — same source
  - Categories (`border`, `color`, `layout`, `legacy`, `motion`, `shadow`, `space`, `typography`, `conventions`) make the violation counts usable as per-category coverage metrics — same source
- **Atlassian enforcement:**
  - The recommended preset is enabled by default, with an explicit "don't maintain your own config" stance. Deprecation tracking is done through `no-deprecated-apis`, `no-deprecated-imports`, `no-deprecated-design-token-usage` and `no-banned-imports` — [eslint-plugin-design-system README](https://www.npmjs.com/package/@atlaskit/eslint-plugin-design-system)
  - Teams are warned about deprecated tokens by ESLint (CSS-in-JS) and Stylelint (CSS) — [ADS: Use tokens in code](https://atlassian.design/foundations/tokens/use-tokens-in-code)
  - An internal Chrome extension shows migration "progress" while toggling themes — [ADS: Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens)
  - The ADS MCP server collects analytics on tool usage, tool parameters, success or failure, agent (`ADSMCP_AGENT`), OS, version and a staff ID. Events are batched every 5 seconds, and users can opt out with `ADSMCP_ANALYTICS_OPT_OUT=true` — [ads-mcp README](https://www.npmjs.com/package/@atlaskit/ads-mcp)
  - Public impact data, from the dark-theme story (June 2023): automated hex-to-token conversion removed "90% of the human work"; 25+ teams manually reviewed screens; 1,200+ images owned by 60+ teams needed theme variants; 5,176 alpha feedback submissions; about 350,000 people using the new themes — [Atlassian blog: The story of dark theme](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme)
- **GitHub Primer:**
  - Migration was tracked as a burn-down of `sx` prop usages in the github.com codebase. Usage peaked at about 7,760 in April 2025. 6,419 were migrated over 6 months by an 8-engineer rotation. The final push went from 895 to 0 in 3 weeks with 2 engineers using Copilot agents, and the migration finished in June 2026 — [GitHub blog, 2026-09-25](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)
  - Other tracking methods: feature-flagged rollout, visual regression tests comparing CSS Modules output with CSS-in-JS, and dashboards of SSR time per service/controller. Result: "55% less time to server-side render a page" — same
  - Deprecations are enforced through autofixable `no-deprecated-*` rules and `use-deprecated-from-deprecated` — package source v9.3.1, [GitHub repo](https://github.com/primer/eslint-plugin-primer-react)
- **Salesforce:**
  - The SARIF report is the measurement artifact: developers "make a note of how many components SLDS Linter has identified for fixing", fix in bulk, and re-lint until there are zero violations — [Trailhead](https://trailhead.salesforce.com/content/learn/modules/salesforce-lightning-design-system-2-for-developers/transition-your-org-from-slds-1-to-slds-2)
  - Public impact data from the Data Cloud case study (2025-08-13): "thousands" of custom components and nearly 3,000 lines of targeted code updated, with thousands of lines of redundant CSS removed. It took 2 engineers one 3-month release, against an estimated 1+ year of manual work. High-confidence errors were auto-fixed in bulk; SARIF categorized the errors; custom scripts and AI-generated summaries supported engineering review — [Salesforce blog](https://www.salesforce.com/blog/data-cloud-slds-2-uplift/)

### Inferences
- The most reusable pattern for Helix is "lint-as-metric". Group rules into coverage categories (Polaris), require a reason on every disable, and emit a machine-readable report (SARIF, as SLDS does) that CI can aggregate across repos.
- Atlassian instruments its MCP server for usage analytics, so agent usage of the design system is itself measured. Helix MCP and skills could log tool calls the same way, with an opt-out flag.
- Primer's public metric is a single countable anti-pattern (`sx` usages) tracked to zero. A Helix CLI could expose `helix report` counts of deprecated/raw-Material usages for the same purpose.

- No public cross-repo usage dashboard (e.g., component import counts per repo) was found for any of the four systems. GitHub, Atlassian and Shopify do not publicly document internal usage tracking beyond what is cited above.

- The Data Cloud post gives no exact auto-fix percentage.
- I found no 2024–2026 Atlassian engineering post with quantified token-adoption or lint-violation numbers. The dark-theme post is from 2023.

The latter is not verified against the primary source.

## Q4. What design decisions and lessons have they published in engineering blogs?

### Takeaway
The published lessons agree on four points:
- Migrate incrementally, using transitional packages and feature flags.
- Automate the mechanical bulk but keep human review.
- Pick metrics you can count down to zero.
- Talk to product teams early.

Codemods are positioned as "assisted", not complete, and AI agents increasingly handle the long tail.

### Cited Findings
- **Atlassian:**
  - "Codemods will be designed to do the heavy lifting, but they'll often not be perfect so some manual work may still be required" — [@atlaskit/codemod-cli README](https://www.npmjs.com/package/@atlaskit/codemod-cli)
  - The token codemod "suggests tokens based on context" and requires manual review — [ADS: Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens)
  - Dark-theme lessons: automation covered about 90% of the work, and gated alpha testing in Jira Labs drove feedback from about 700 per week down to about 17 per week — [Atlassian blog](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme)
  - The ESLint rule table is codegen'd, and the plugin ships education-only rules (`prefer-primitives`) alongside enforcement — [README](https://www.npmjs.com/package/@atlaskit/eslint-plugin-design-system)
- **GitHub Primer:**
  - Incremental migration via the `@primer/styled-react` wrapper allowed parallel adoption. Feature flags and visual regression tests reduced risk. An internal codemod plus a VS Code extension handled the conversions, and Copilot agents finished the long tail — [GitHub blog, 2026-09-25](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)
  - v38 made the break explicit: sx removed, ESM-only — [primer/react #7086](https://github.com/primer/react/discussions/7086)
- **Salesforce Data Cloud:** Four decisions — [Salesforce blog, 2025-08-13](https://www.salesforce.com/blog/data-cloud-slds-2-uplift/):
  - Convert hard-coded values to styling hooks *with fallbacks*, e.g. `var(--slds-g-color-surface-1, #FFF)`.
  - Update deprecated tokens and utility classes.
  - Mitigate gaps where hooks don't cover every value.
  - Communicate early about low-risk changes.

  The fallback requirement is enforced by the `no-slds-var-without-fallback` lint rule — [eslint-plugin-slds README](https://www.npmjs.com/package/@salesforce-ux/eslint-plugin-slds)
- **Shopify:** The platform pivot from Polaris React (deprecated, maintenance only) to CDN-loaded Polaris web components froze the React-era lint and codemod tooling (archived 2026-09-11). Migration effort moved to AI-toolkit skills — [Shopify/polaris README](https://raw.githubusercontent.com/Shopify/polaris/HEAD/README.md); [GitHub archive](https://github.com/Shopify/polaris/tree/main/stylelint-polaris); [community.shopify.dev](https://community.shopify.dev/t/speed-up-migrating-your-checkout-and-customer-account-ui-extensions-to-polaris-web-components-with-the-shopify-ai-toolkit/35092)

### Inferences
- For Helix: ship the lint plugin and recommended preset first, since every system treats that as the enforcement backbone. Make autofix produce token substitutions with perceptual nearest-match suggestions (SLDS ΔE approach) and require fallbacks.
- Make migrations reportable (SARIF/JSON counts by category), and pair codemods or schematics with agent skills for the long tail.
- Shopify's experience suggests tooling should be decoupled from one framework binding, so it survives a platform change such as Angular Material to web components.

### Gaps
- I found no Shopify engineering blog (2024–2026) quantifying Stylelint-Polaris coverage results.
- The Primer blog post was read through a summarizer. Exact quotes beyond the numbers cited should be re-checked against the original.
