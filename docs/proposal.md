# Make the Helix CLI the agent's verification loop

By 2026 the design-system tooling market has settled on a three-part shape. **Skills** carry the knowledge. A **lean MCP server**, where there is one, handles discovery. A **CLI** is the only thing that changes files or checks them. The Stripe story that made an impact is evidence for that shape, not a product to copy. Publicly, Stripe launched **Stripe Projects**, an agent-first CLI that provisions whole production stacks and has nothing to do with design systems. Internally, Stripe's design team **replaced an MCP server over its Sail docs with a custom CLI**, after the same prompt from three people produced three different interfaces. The CLI serves page templates, workflows and machine-readable rules in phases. Angular and Nx made the same move in 2026, cutting their MCP tool surfaces in favour of skills plus CLI and schematics. The basics are now table stakes: `--json`, non-interactive flags, dry-run, `setup --client`, `npx skills add`, lint presets with autofix and versioned codemods. What sets the leaders apart is a **validation loop** agents must close (Primer's `lint_css`, Shopify's component validator, Salesforce's SARIF-to-zero uplift) and an **agent hand-off for migration leftovers** (Ant Design, React Spectrum). The biggest gap is that **no adoption scanner works on Angular templates**: Omlet, react-scanner, Storybook's manifest on Webpack Angular and the shadcn registry are all React-first. For Helix, that gap is the opening. The Helix CLI should not become another component catalogue. It should be the one place that measures Helix adoption in Angular code, fixes the mechanical part, serves the Helix templates and rules on demand, and gives agents a pass/fail check to work against. The first piece to build is `helix scan`, which turns the ~665 hard-coded colours and ~690 Material-internal overrides in the consumer apps into a baseline that CI enforces and agents can work down.

The anchor of the whole design is that **Helix already has a canonical, machine-readable definition of itself**: the Helix Angular design system, generated from the implementation so it cannot drift. The CLI reads from that definition rather than from Figma, Supernova or a second documentation site. This keeps the tool small, vendor-free and entirely inside the Angular world the apps already live in.

One scope note frames everything below. Helix is **breaking away from the legacy `@cdx/*` packages** and shipping under its own scope, **`@hlx/*`** (working name; the binary stays `helix`), with no `@cdx` dependency. That re-platform is engineering work in the implementation repo (`cdx-next`), not the subject of this proposal — **the CLI's job is to measure, ratchet and assist the break, not to perform it.** For the scanner, legacy `@cdx/*` imports and `cdx-*` selectors are debt; the compliant target is `@hlx/*`, the `hlx-*` classes and themed `mat-*`. Because the consumer apps are all on `@cdx` today (one pinned to `@cdx` 18.3), the move is itself a large, countable migration, which plays to the CLI's strength: turning a migration into a number that can only go down.

## Stripe's lesson was to swap MCP for a CLI, not to launch one

"Stripe launched a CLI" refers to two different things, and only one of them matters for Helix. The public launch was **Stripe Projects**. It went to developer preview on 26–27 March 2026 and reached GA at Stripe Sessions 2026 with 32 providers. It lets an agent provision hosting, databases, auth, analytics and AI services from the terminal, with credentials synced and billing in one place ([projects.dev](https://projects.dev/blog/production-ready-dev-stack-from-terminal/); [byteiota](https://byteiota.com/stripe-projects-ga-ai-agents-provision-dev-stack/)). It went from idea to preview in **seven weeks**. Stripe argued that the bottleneck for agents is not single API calls but the work around them: accounts, auth, credentials and billing ([projects.dev](https://projects.dev/blog/how-we-built-stripe-projects-in-seven-weeks/)). Around it, the Stripe CLI gained `stripe agent setup`. This command detects which coding agents you use and installs a plugin that configures Stripe's MCP server and installs skills that keep themselves up to date. Stripe also publishes a machine-readable skills index at `/.well-known/skills/index.json` for agents that cannot run `npx skills` ([Stripe docs](https://docs.stripe.com/skills.md)).

The design-system story is the one that matters for Helix. Stripe's Head of Design, Katie Dill, described it at the Lenny and Friends Summit (reported 10 September 2026). She named the problem **"Zombie UI"**: generic interfaces with no brand, produced by AI. Stripe first connected agents to Sail's documentation through an MCP server and found that **the same prompt from three users produced three different outputs**. It then built a **custom CLI on top of the design system** that serves complete page templates and workflows rather than single components. The CLI delivers documentation "at the right moment", in phases, to avoid context rot, and encodes strict design rules as machine-readable specs. Quality control moved to after the build, with an editorial review of finished interfaces ([Dr. Web](https://www.drweb.de/zombie-ui-stripe-design-system-ki/)). The evidence is thin. The only source is a German secondary article, no transcript was found, and Sail and its CLI are not public. The lesson is still clear, and the rest of the market backs it up: **giving agents access to documentation does not make them follow the brand**. What works is giving them templates, rules scoped to the task, and a checker.

Two Stripe patterns apply directly to Helix. The first is `stripe agent setup`: one command that detects the agent, installs skills and configuration, and keeps them updated. This is what the existing `helix-ai sync` already does in part. The second is the Sail CLI's progressive serving of templates and rules. Helix already has the templates to serve: the Helix Angular design system ships a `Template*` family of about twenty-one composed page and section patterns — nine of them for AI interfaces — each with a when-to-use, an anatomy, machine-checkable rules and a live preview. Those AI chat UIs have been rebuilt five times across consumer apps. That is the same "three users, three outputs" failure Stripe described, and `helix template get ai-assistant` is the direct answer.

## Every serious design system now ships skills, a thin MCP and a CLI that changes or checks files

Across about twenty systems surveyed, the same architecture keeps appearing. **shadcn** is the reference CLI for distributing components. Version 4.21.3 covers `init`, `add` (with `--dry-run`, `--diff` and `--view`), `search`, `view`, `docs --json`, `info --json`, `apply`, `migrate`, `eject`, `registry validate` and `mcp init --client`. It also ships an Agent Skill and an MCP server whose seven tools are all read-only. The install tool `get_add_command_for_items` *returns a CLI command for the agent to run* instead of writing files itself ([shadcn CLI](https://ui.shadcn.com/docs/cli); [shadcn MCP source](https://raw.githubusercontent.com/shadcn-ui/ui/main/packages/shadcn/src/mcp/index.ts)). At **~13.4M weekly downloads** it dwarfs every per-library CLI. Park UI's CLI, with ~4k a week and little activity, shows that standalone "add component" tools lose to shared formats ([npm API](https://api.npmjs.org/downloads/point/last-week/shadcn)). **Ant Design's `@ant-design/cli`** is the broadest single design-system binary found. It has offline `info`, `doc`, `demo`, `token` and `changelog` lookups, plus project commands `doctor`, `usage` and `lint`. Its `migrate <from> <to> --apply` command emits an "agent-ready migration prompt". `antd mcp` is built into the CLI, `setup --client` writes agent configuration, and everything supports `--format json` ([Ant Design: For Agents](https://ant.design/docs/react/for-agents)).

The enterprise systems split enforcement from knowledge. **Atlassian** has 83 ESLint rules, 30 of them autofixable, and tells teams not to maintain their own configuration. It runs codemods through `@atlaskit/codemod-cli`, with `--since-ref` and `--packages pkg@fromVersion`, and through Hypermod. Its `@atlaskit/ads-mcp` server includes axe-core accessibility analysis and **records tool-usage analytics with an opt-out** ([eslint plugin README](https://www.npmjs.com/package/@atlaskit/eslint-plugin-design-system); [codemod-cli](https://www.npmjs.com/package/@atlaskit/codemod-cli); [ads-mcp](https://www.npmjs.com/package/@atlaskit/ads-mcp)). **Salesforce** is the closest model to a single design-system CLI. `@salesforce-ux/slds-linter` offers `lint`, `lint --fix`, `report` (SARIF output) and `emit`, wraps its own ESLint plugin, and feeds an MCP tool, `orchestrate_lwc_slds2_uplift`, that works from the linter's output. Its `no-hardcoded-values-slds2` rule suggests the nearest styling hook by **CIEDE2000 ΔE** colour distance ([slds-linter](https://github.com/salesforce-ux/slds-linter); [eslint-plugin-slds](https://www.npmjs.com/package/@salesforce-ux/eslint-plugin-slds); [LWC MCP](https://developer.salesforce.com/docs/platform/lwc/guide/mcp-lwc.html)). **GitHub Primer's** MCP includes `lint_css`, which runs Stylelint with autofix on CSS the agent writes. Its instructions tell the agent the "task is incomplete without a success message" and include token bundles for each UI pattern to stop "property-by-property searching" (`@primer/mcp` v1.1.0 source; [primer.style MCP](https://primer.style/product/getting-started/foundations/mcp)). **Shopify** handled its Polaris React to web components move with agent skills and an MCP validator, `validate_component_codeblocks`, which rejects hallucinated components and props. It did not write new codemods, and its Stylelint and codemod packages have been frozen since March 2025 ([Shopify community](https://community.shopify.dev/t/speed-up-migrating-your-checkout-and-customer-account-ui-extensions-to-polaris-web-components-with-the-shopify-ai-toolkit/35092); [policylayer](https://policylayer.com/tools/dev/validate-component-codeblocks)).

The Angular ecosystem matters most for Helix, and its own platform owners point the same way. The Angular CLI's `ng mcp` server **dropped `find_examples` and `modernize` in April–May 2026** and folded build, test and e2e into one `run_target` tool. In place of a dedicated migration tool, agents now get "instructions for schematic discovery", so they find and run `ng update` migrations themselves ([angular-cli commits](https://github.com/angular/angular-cli/commits/main/packages/angular/cli/src/commands/mcp/tools)). Nx did the same in February 2026. `npx nx configure-ai-agents` writes AGENTS.md or CLAUDE.md plus skills for six agents, and the Nx MCP now defaults to `--minimal`, with workspace and generator tools hidden. Nx says MCP is "for connecting to remote services" ([Nx blog](https://nx.dev/blog/nx-ai-agent-skills); [Nx MCP reference](https://nx.dev/docs/reference/nx-mcp)). Among Angular component libraries, **Spartan** is the closest structural match to a Helix CLI. One package works as both an Angular schematic collection and an Nx plugin, has an `info --json` command that its own agent skill reads, and has a 17-tool MCP with health tools ([spartan.ng CLI](https://www.spartan.ng/documentation/cli); [skills](https://www.spartan.ng/documentation/skills)). **Kendo** moved major-version migrations out of `ng update` into `@progress/kendo-cli migrate`, a codemod CLI. Its MCP "Upgrade Assistant" runs the codemods, then uses AI to fix the remaining compile errors. Users have complained that the codemods reformat their HTML templates ([Telerik](https://www.telerik.com/kendo-angular-ui-develop/components/assisted-migration); [feedback 1696502](https://feedback.telerik.com/kendo-angular-ui/1696502-kendo-cli-migration-tool-option-to-suppress-automatic-reformatting-of-angular-html-templates)). **PrimeNG** ships a read-only MCP with `validate_usage` and `get_setup`, bundled with skills as a plugin ([primeng.dev/mcp](https://primeng.dev/mcp)).

## Table stakes are flags and installers; the edge is a gate agents must pass

The baseline is easy to state because almost everyone meets it. An agent-friendly CLI makes every input a flag and only prompts when a TTY is present. It supports `--json` or `--output json`, distinct non-zero exit codes for each failure type, `--non-interactive` or `--yes`, and `--dry-run`, and it leaves out spinners that waste context tokens ([Speakeasy](https://www.speakeasy.com/blog/engineering-agent-friendly-cli); [Layer5](https://layer5.io/blog/ai/design-for-the-human-enable-the-agent)). Each subcommand should document itself, so commands the agent is not using stay out of its context ([Vaughan](https://codex.danielvaughan.com/2026/04/28/building-agent-friendly-clis-codex-cli-composable-tool-design/)). On the knowledge side, the 2026 "AI-ready design system" kit has four parts: an `llms.txt` with a `.md` version of each page, installable Agent Skills through Vercel's `npx skills add` (which reaches 18+ agents), a one-line setup per client, and usually a docs MCP. Carbon, MUI, React Spectrum, PatternFly, Ant Design, Primer, Atlassian and Chakra all ship some version of it ([Vercel skills](https://vercel.com/changelog/introducing-skills-the-open-agent-skills-ecosystem); [React Spectrum AI](https://react-spectrum.adobe.com/ai); [Carbon MCP](https://carbondesignsystem.com/developing/carbon-mcp/onboarding-and-setup/)). On the code side, a recommended ESLint and Stylelint preset with autofix for token and deprecation rules is standard, as are versioned codemods that dry-run by default and need an explicit `--write` (Carbon, MUI, Canvas Kit, Paste, PatternFly) ([Carbon migration guide](https://carbondesignsystem.com/migrating/guide/develop); [MUI v7](https://mui.com/material-ui/migration/upgrade-to-v7/)). Helix already meets much of this baseline through helix-skills, the lint presets and `helix-ai sync`. What it lacks against peers is a `--json` contract, a `.well-known` skills index, and a single binary.

Four capabilities separate the leaders. The first is **validation the agent cannot skip**. Primer's `lint_css` gate, Shopify's anti-hallucination validator, PrimeNG's `validate_usage` and shadcn's `get_audit_checklist` all move design-system compliance from "the agent read the docs" to "the agent's output passed a check". This is the step Stripe's CLI encodes as rules. The second is **lint as a metric**. Polaris's `polaris/coverage` meta-rule groups violations into categories (color, space, typography, motion, and so on) and requires a stated reason for every disable comment, which makes opting out auditable ([stylelint-polaris](https://www.npmjs.com/package/@shopify/stylelint-polaris)). SLDS treats the SARIF violation count as the measure of progress, and zero means "uplifted" ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/salesforce-lightning-design-system-2-for-developers/transition-your-org-from-slds-1-to-slds-2)). The third is **an agent hand-off for whatever automation cannot finish**: Ant Design's `--apply` prompt, React Spectrum's `--agent` mode with a matching migration skill, and `TODO(S2-upgrade)` markers in code ([React Spectrum: Migrating](https://react-spectrum.adobe.com/migrating)). The fourth is **templates and rules served in phases rather than whole documents**, the Stripe pattern, which Primer's per-pattern token bundles come close to — and which Helix can do straight from its template catalog.

The impact data supports the last three. Primer tracked one countable anti-pattern, `sx` prop usage, from a peak of ~7,760 down to zero. An eight-engineer rotation migrated 6,419 over six months, then **two engineers with Copilot agents cleared the last 895 in three weeks** ([GitHub blog](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)). Salesforce Data Cloud uplifted thousands of custom components with **two engineers in one three-month release, against an estimated year or more of manual work**, using bulk autofix and SARIF triage ([Salesforce blog](https://www.salesforce.com/blog/data-cloud-slds-2-uplift/)). Atlassian's hex-to-token automation removed about **90% of the human work** in its dark-theme migration, and its codemod docs warn that results "will often not be perfect" ([Atlassian blog](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme); [codemod-cli](https://www.npmjs.com/package/@atlaskit/codemod-cli)). The common recipe is a counter that can reach zero, automation for the mechanical bulk, and agents for the rest. No public evaluation shows that any design-system MCP improves output quality. The case for "CLI plus skills over MCP" rests on practitioner reports (Stripe, Angular, Nx), not on controlled data.

## Nobody measures design-system adoption in Angular templates

The clearest gap is measurement for anything other than React. **Omlet**, the leading adoption SaaS, scans React and React Native only, and Angular has been listed as "coming soon" without shipping ([npm @omlet/cli](https://www.npmjs.com/package/@omlet/cli)). **react-scanner**, the open-source scanner behind Elastic EUI's `eui-usage-analytics` and Brevo's adoption tracking, parses only JSX ([react-scanner](https://github.com/moroshko/react-scanner); [EUI usage analytics](https://github.com/elastic/eui/tree/main/packages/eui-usage-analytics); [Brevo](https://engineering.brevo.com/how-to-track-design-system-adoption/)). Ant Design's `antd usage` and Panda's `analyze` show that a usage report belongs inside the design-system CLI, but both are React or CSS-in-JS ([Panda CLI](https://panda-css.com/docs/references/cli)). The surrounding agent tooling is just as React-first. The Storybook MCP's docs toolset needs a component manifest that the Webpack-based `@storybook/angular` builder does not produce, only `@storybook/angular-vite` does ([Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview)). `storybook ai setup` supports React + Vite only. shadcn's registry, which v0 uses to pass "context from your design system to AI models", is a React distribution format ([v0 docs](https://v0.app/docs/design-systems)). An Angular and Material 3 team gets almost none of this out of the box.

Two further gaps follow. First, **nobody closes the loop as one agent-runnable sequence** of scan, structured violations, fix, and re-scan. SLDS comes closest, but it targets Salesforce's own LWC and Aura stack. Second, **adoption has no agreed definition**. Practitioners report disagreement over what counts as a component and how to measure coverage ([guild.host](https://guild.host/presentations/measuring-the-unmeasurable-jucx6n)), and the alternatives range from import counts to pixel-based "visual coverage" ([guild.host](https://www.guild.host/presentations/measuring-design-systems-s7985q)). Third, **codemod platforms do not handle Angular templates well**. Codemod.com, Hypermod and GritQL are JavaScript and TypeScript first, with no confirmed support for Angular HTML templates ([Codemod](https://github.com/codemod/codemod); [Honeycomb/Grit](https://www.honeycomb.io/blog/honeycomb-acquires-grit)). The research also found nothing on how agents authenticate to a private npm registry from a sandbox, which matters directly for the Helix scope on Artifactory.

These gaps line up with Helix's situation. Adoption in the three consumer apps has not started. Their debt can be counted: ~665 hex colours, ~690 `.mat-mdc-*` and `::ng-deep` overrides, the legacy `@cdx` scope with one app a version pin four majors behind, and loading, empty, error and chat states built by hand. Helix also already holds the pieces that peers lack: a canonical generated definition of the system, a template catalog, lint presets, a checker, a sync command and a public skills repo. What is missing is the part that ties them together: **a measurement and verification command that understands Angular templates and SCSS, and reads the Helix definition rather than a vendor's.**

## A Helix CLI should measure, verify, guide and hand off, in that order

### Source of truth: the implementation ships it, the Helix Angular artifact defines it, the CLI snapshots it

The design rests on one split that must stay sharp.

**The Helix implementation is the implementation source of truth.** The `@hlx/*` packages an app installs, the Angular Material (M3) theme Sass, the branded shell components, the Storybook stories and the `docs-website` pattern examples all live in the implementation repo (`cdx-next` today, being re-homed as Helix breaks away from the legacy `@cdx` scope). App code imports these packages, so they are what `helix scan`, `fix` and `verify` measure code *against*.

**The Helix Angular design system is the canonical definition.** It is a Claude Design artifact that holds `tokens.json`, a component manifest (one folder per component, with guidelines, the `.d.ts` API and a live preview), the `Template*` catalog, and the foundations and usage rules as Markdown. Crucially it is **generated from the implementation and is wired so it cannot drift**: the token map references the Sass tokens, and every component and template preview renders the real Storybook story (`Components/*` and `Patterns/*`), not a redraw. That no-drift guarantee is exactly what lets the CLI treat the artifact as authoritative instead of maintaining its own copy of the rules.

The CLI consumes the definition, in one direction, and never over the network at runtime:

```
Helix implementation  ──generators (theme Sass, Storybook, docs-website patterns)──▶  Helix Angular artifact
Helix Angular artifact  ──release-time export──▶  @hlx/cli bundled snapshot (versioned JSON)
Helix implementation  ──npm publish to Artifactory──▶  @hlx/* packages  ──▶  what the scanner measures
```

`@hlx/cli` ships a versioned snapshot of the artifact's `project/` data (tokens, component manifest, templates, rules), so the CLI works in CI and in agent sandboxes that cannot reach claude.ai or Figma, and **needs no `@hlx/*` package installed to run** — the snapshot is self-contained. The snapshot version moves in step with the Helix major. Because there are two sources of truth — the definition (artifact) and the implementation (installed packages) — **reconciliation is a first-class job, not an assumption**: `helix doctor` fails if the snapshot's token names or component selectors disagree with what the installed `@hlx/*` packages export, and flags any lingering `@cdx/*`. This is the mechanism that keeps the split honest, and the only point at which the CLI touches installed packages at all.

Three things follow directly, and each is a dependency the earlier draft carried and this one drops. Figma drift detection, Code Connect `.figma.ts` templates and the Figma MCP are **out**: the artifact already carries the Angular-and-M3 definition, so there is no second design surface to diff against. Supernova is **out**: it was only "the platform that holds the system and shows a dashboard", and the artifact holds the system while a scheduled aggregator over `helix scan` JSON shows the dashboard. And the legacy **`@cdx` scope is out**: the re-platform to `@hlx/*` is engineering work in the implementation repo, outside this proposal, but the CLI treats the transition as a measured migration (below). The single-source pipeline that used to be described as "`*.guide.md` feed docs, skills and Storybook" is now stated at the right layer: the implementation generates the artifact, and the artifact is what the CLI, the docs and the skills all read.

### Positioning: one binary, built around compliance rather than a catalogue

The Helix CLI should be a single private package, **`@hlx/cli`, exposing a `helix` binary**. It should absorb `helix-check` (keeping it as an alias that calls `helix doctor`) and the existing `helix-ai sync` (which becomes `helix agent sync`). Its purpose in one sentence: *the Helix CLI tells a team or an agent how far an Angular app is from Helix, fixes the mechanical part, serves the Helix templates and rules on demand, and gives a deterministic pass/fail check.* It should not try to compete with shadcn on distributing components. Helix ships npm packages, not copied source, and Panda's config-driven `analyze`/`check`/`--json` model fits a package-based system better than shadcn's "add" model ([Panda CLI](https://panda-css.com/docs/references/cli)). Nor should it be a second documentation site. Knowledge lives in the Helix Angular definition, and the CLI serves slices of it from the snapshot when asked. Following Salesforce, the CLI should **wrap the existing engines, not replace them**. The Helix ESLint config (`@hlx/eslint-config-helix`), using `@angular-eslint`'s template parser for HTML and TypeScript, and the Helix Stylelint config (`@hlx/stylelint-config-helix`) for SCSS stay the single rule catalogue, and `helix scan` runs them, combines the results and turns them into metrics. Rules then exist in one place, editors and CI show the same rule IDs, and the CLI adds categorisation, baselines, metrics and agent-ready output.

### Command surface

| Command | Purpose | Key flags | Precedent |
|---|---|---|---|
| `helix doctor` | Environment health (absorbs helix-check): Node, `.npmrc`/registry reachability, `@hlx` version skew vs Helix major, theme class, fonts, Storybook builder, agent config present; **reconciles the bundled snapshot against the installed `@hlx/*` packages** (token names, selectors); flags any legacy `@cdx/*` | `--json`, `--fix`, `--offline` | Storybook `doctor`, Spartan healthcheck, `antd doctor` |
| `helix scan [path]` | Adoption + debt metrics over templates, TS, SCSS | `--format json\|sarif\|text`, `--baseline <file>`, `--fail-on regression\|any\|none`, `--category`, `--changed-since <ref>` | Polaris coverage, SLDS `report`, `antd usage` |
| `helix fix [category]` | Mechanical autofix (colour → nearest **semantic `--hlx-*`** token with fallback, deprecated imports, banned overrides where safe) | `--dry-run` (default), `--write`, `--min-confidence 0.8`, `--json` | SLDS `lint --fix` + ΔE, Carbon `--write` |
| `helix verify` | The agent gate: scan scoped to changed files + doctor, fails on any new violation | `--changed-since <ref>`, `--json` | Primer `lint_css`, shadcn audit checklist |
| `helix template list/get <name>` | Serve templates from the snapshot in phases (overview → anatomy → rules → a11y → uses/preview) | `--step`, `--json` | Stripe Sail CLI, Primer token bundles |
| `helix rules <file\|component>` | Rules relevant to *this* file's imports/selectors only | `--json` | Stripe phased rules |
| `helix component list/get <selector>` | Component manifest from the snapshot: selector, inputs/outputs, tokens, variants, examples, do/don't | `--json` | antd `info`, PatternFly JSON schemas |
| `helix migrate` | Orchestrate `ng update` per major, then scan, then emit leftover tasks | `--to 22`, `--step`, `--agent`, `--json` | Kendo migrate, Spectrum `--agent`, antd `--apply` |
| `helix agent setup/sync` | Detect agents, write skills + AGENTS.md/CLAUDE.md managed blocks + Copilot instructions (+ MCP later) | `--client claude\|copilot\|cursor\|codex`, `--check` | `stripe agent setup`, `nx configure-ai-agents`, Angular `ai-config` |
| `helix export design-md` | Emit DESIGN.md from the snapshot tokens for Stitch/Claude Design | `--out` | Google DESIGN.md |
| `helix mcp` (Phase 4) | Thin stdio wrapper over the same `--json` commands | `--read-only` | `antd mcp` |

Every command follows one contract. Input comes only from flags, with prompts only when a TTY is present. Machine output goes to stdout and logs to stderr. Exit codes are fixed: **0** pass, **1** violations over threshold, **2** usage or config error, **3** environment failure (doctor, including a snapshot↔package mismatch), **4** regression against baseline. Commands never change files without `--write`. The scan report should be versioned and readable in both directions, by people and by agents:

```json
{
  "schemaVersion": "1.0",
  "tool": { "name": "helix", "version": "22.2.0" },
  "snapshot": { "artifact": "helix-angular", "version": "22.2.0", "reconciled": true },
  "project": { "root": ".", "hlxVersion": null, "legacyCdxVersion": "18.3.0", "helixMajor": 22, "angular": "18.2.0" },
```

### Adoption measurement for Angular templates

`helix scan` should parse templates with the Angular compiler, through `@angular-eslint/template-parser`, so it sees inline and external templates, structural control flow and attribute selectors exactly, rather than using regular expressions. It parses SCSS with the Stylelint and PostCSS stack. It should sort every UI element into four groups. **Helix** covers `hlx-*` components, classes and directives. **Material-themed** covers `mat-*` under a Helix theme, which counts as compliant because Helix is Material 3. **Raw equivalents** are `<button>`, `<input>`, `<select>`, `<table>` and similar elements where a Helix or Material component exists. **Custom** covers app components. During the break from `@cdx`, legacy `cdx-*` selectors and `@cdx/*` imports are counted as debt in their own category, so the migration shows up as a number alongside coverage. Coverage is then (Helix + Material-themed) ÷ (Helix + Material-themed + raw equivalents). Custom components are reported separately, because a custom component is not automatically a failure.

Style debt follows Polaris's categories (color, space, typography, shape, motion, overrides) and counts hard-coded values, `.mat-mdc-*` selectors, `::ng-deep` and `!important`. Two debt rules come straight from how Helix exposes itself. First, the only tokens an app should consume are the **semantic `--hlx-*` custom properties** (`var(--hlx-text-primary)`, `var(--hlx-surface-minimal)`, `var(--hlx-spacing-3)`, `var(--hlx-gradient-ai)`); the primitive ramps (`color-*`, `ref-*`) and component-internal tokens (`components-*`) are intentionally not exposed, so a reference to one in app code is debt (`nonSemanticToken`). Second, per-app `::ng-deep` styling of rendered markdown is debt, because the theme ships an `hlx-prose` class for exactly that. **Disable comments without a stated reason count as debt**, using Polaris's `reportDescriptionlessDisables` approach. Template candidates for hand-rolled page states (loading, empty, error) and AI chat UIs come from heuristics, such as a spinner inside a conditional block with no `hlx` state component, or a bespoke chat thread with no shared assistant template. They are labelled "candidates" with a confidence score and kept out of the headline coverage number, because heuristic counts are easy to dispute, and they map to named templates (`TemplatePageStates`, `EmptyState`, `TemplateAiAssistant`) so the fix is a pointer, not just a count.

The most important design choice is the **baseline ratchet**. Nobody will fix 665 colours in one go, so `helix scan --baseline` stores per-file counts and `--fail-on regression` fails CI only when a count goes up. Every merged change can then only improve the numbers, and the trend becomes the adoption chart. This is Primer's burn-down to zero applied to every category, and it is the most useful thing the CLI can do for the three consumer apps. For organisation-wide dashboards, CI should upload the JSON as a build artifact that a scheduled job aggregates into a static dashboard. This is the EUI approach without phoning home, and it replaces the earlier plan to lean on Supernova for the dashboard. Any telemetry from `helix agent` or `helix mcp` usage should follow Atlassian's opt-out design ([ads-mcp](https://www.npmjs.com/package/@atlaskit/ads-mcp)).

### The token model and autofix

Because the snapshot carries `tokens.json`, `helix fix color` has a precise target set. It filters to the **exposed semantic tokens**, computes the CIEDE2000 ΔE between a hard-coded colour and each semantic token's value, and proposes the nearest one as `var(--hlx-<name>, #hex)` — keeping the original hex as the fallback so the visual result stays reviewable, as SLDS does ([eslint-plugin-slds](https://www.npmjs.com/package/@salesforce-ux/eslint-plugin-slds)). It never proposes a primitive (`color-neutral-800`) or a component-internal token (`components-primary-filled`), because those are not consumable. A confidence threshold (`--min-confidence`) and dry-run-by-default keep unsafe substitutions out. Edits must be surgical text replacements at the compiler's source positions, never re-printed templates, to avoid the reformatting complaint Kendo users raised. For this to be correct, the snapshot's token `name` and the exposed `--hlx-*` custom property must line up with what the Helix theme package (`@hlx/theme-angular-material`) actually emits — which is precisely what `helix doctor` reconciles, so a package upgrade that renames or drops a token fails loudly instead of producing wrong fixes.

### Guiding new work: serve the templates in phases

Measuring, fixing and verifying all act on code that already exists. Guiding new work is about making the first draft Helix-correct, and it is where the template catalog earns its place. The Helix Angular definition already carries, per template, a *when to use* and *avoid when*, an *anatomy*, machine-checkable *rules* (announce streaming into `aria-live`, feedback as real `<button>`s, compose all four page states, applied filters as the source of truth, and so on), the list of components it *uses*, and a live preview. `helix template get ai-assistant --step structure` serves one slice at a time instead of a whole document, which is the Stripe mechanism and the fix for context rot. Because the team keeps extending the catalog, the CLI reads the list from the snapshot rather than hard-coding it, and a new template is available to agents as soon as the snapshot is re-exported. `helix rules <file>` returns only the rules that apply to the imports and selectors in the file in front of the agent. `helix component get <selector>` returns the manifest entry for one component. All three are the same snapshot data at different granularities.

The skills in the public `uh-joan/helix-skills` repo should change from mainly reference material into **procedures that call the CLI**. Each skill should be 50–100 lines with explicit triggers, following Speakeasy's guidance. A new `helix-adoption` skill would run `helix scan --format json`, pick the highest-impact category, run `helix fix --dry-run` and then `--write` at a confidence threshold, handle what remains by hand using `helix rules <file>`, and **treat the task as unfinished until `helix verify` exits 0**. That last line is the same instruction Primer's MCP gives for `lint_css`. The existing `helix-patterns` skill should fetch `helix template get ai-assistant --step structure` one step at a time instead of loading all the guides at once. That is the Stripe mechanism, and it directly targets the five rebuilt chat UIs. `helix agent setup` should **add to, not overwrite**, the files Angular's `ai-config` schematic and `nx configure-ai-agents` generate, keeping Helix content inside its managed block ([ai-config schema](https://raw.githubusercontent.com/angular/angular-cli/main/packages/schematics/angular/ai-config/schema.json)). Publishing `/.well-known/skills/index.json` on the Helix docs site, as Stripe and Nx do, lets agents fetch skills without `npx skills` ([Nx AI setup](https://nx.dev/docs/getting-started/ai-setup)).

### Agent-native design: skills and CLI first, MCP only as a thin wrapper

The evidence supports **skills plus a CLI as the main agent interface**, with MCP added later as a thin wrapper. Stripe left MCP-over-docs because output was inconsistent. Angular removed bespoke MCP tools in favour of agents discovering schematics. Nx hid generator tools behind `--no-minimal` and moved knowledge into skills. Angular's tool set changed about five times in 2026, which shows how unstable MCP tool surfaces still are ([angular-cli commits](https://github.com/angular/angular-cli/commits/main/packages/angular/cli/src/commands/mcp/tools); [Nx blog](https://nx.dev/blog/nx-ai-agent-skills)). The strongest argument for MCP points the other way. Primer, Shopify and PrimeNG get real value from *validation* tools, and some hosts, such as IDE Copilot setups, find MCP tools more easily than shell commands. Helix can have both by putting the logic in the CLI and, in Phase 4, exposing `helix mcp` with a handful of tools (`scan`, `verify`, `get_template`, `get_rules`, `get_component`) that call the same functions and return the same JSON. This follows the Ant Design model ([Ant Design MCP](https://ant.design/docs/react/mcp.md)). Docs-search tools are not worth building. That is the part Stripe found unreliable.

### Migration: schematics for version moves, lint autofix for debt, agents for what is left

Three migration problems need distinct mechanisms. The new one is the **scope move off `@cdx`**: rewriting `@cdx/*` imports to `@hlx/*` and `cdx-*` selectors to `hlx-*`. That belongs in a codemod shipped with `ng-add`/`ng update` for `@hlx`, and `helix scan` counts the remaining legacy usage so the move is a ratcheted number, not a flag day. The re-platform in the implementation repo is out of scope here; the CLI's part is the codemod and the count. **Version moves**, such as the legacy `@cdx` 18.3 to Helix 22, belong in **`ng update` schematics**. Fields in `package.json` (`schematics`, `ng-update.migrations`) make them discoverable by the Angular CLI, Nx (`nx migrate` runs Angular ng-update migrations) and the Angular MCP's schematic discovery, with nothing extra to install. `--create-commits` gives one commit per migration ([angular.dev schematics](https://angular.dev/tools/cli/schematics-for-libraries); [ng update](https://angular.dev/cli/update)). Helix should ship an `ng-add` in two phases, setting up dependencies, theme, fonts and AI configuration the way Material and Taiga do, plus one migration per major ([Material collection.json](https://raw.githubusercontent.com/angular/components/main/src/material/schematics/collection.json)). Material removes old migrations each major ([migration.json](https://raw.githubusercontent.com/angular/components/main/src/material/schematics/migration.json)), so the pinned app has to step through 19, 20, 21 and 22 on the matching Helix versions. `helix migrate --to 22` should run those steps in order, run `helix scan` after each one, and stop at the first step that leaves the build broken. `ng update` has no documented `--dry-run`, so the orchestrator should insist on a clean git tree and use per-step commits as its rollback. **Style debt is not tied to an update moment.** It should live as lint rules with autofix and be applied through `helix fix`, using SLDS's ΔE nearest-token matching against the semantic tokens and its rule that replacements carry fallbacks (`var(--hlx-token, #hex)`), so visual changes stay reviewable. Whatever automation cannot do, such as replacing a hand-rolled empty state with the Page states template, becomes `TODO(helix-upgrade)` markers plus a JSON task list from `helix migrate --agent`, which the `helix-adoption` skill works through. Generic codemod platforms (Codemod.com, Hypermod) are not worth adopting until they handle Angular templates.

### Packaging and distribution across a private registry and a public skills repo

The split should be deliberate. **Executable logic and Helix-specific data are private. Instructions are public.** `@hlx/cli` ships from Artifactory and depends on nothing outside the `@hlx` scope and the Angular, ESLint and Stylelint toolchain the app already has. Its rule data, component manifest and template catalog come from the Helix Angular snapshot, exported at build time from the same artifact that is itself generated from the implementation, so the definition, the docs, the skills and the CLI cannot drift. The CLI version moves in step with the Helix major so that `helix doctor` can compare a project against the Helix version it targets and reconcile the snapshot with the installed packages. The public helix-skills repo stays installable through `npx skills add uh-joan/helix-skills`, but every skill must handle **a missing CLI**. Agents in cloud sandboxes may not be able to reach repo.clarivate.io. When `helix` cannot be found, the skill should report the cause (`.npmrc` scope mapping or token) and fall back to guidance only, without guessing. This matters more than it looks. The research found no established pattern for agent access to private registries, so Helix should document a least-privilege, read-only Artifactory token for `@hlx` and treat it the way Stripe treats restricted API keys ([Stripe MCP](https://docs.stripe.com/mcp)). Bundling the snapshot inside the package is what lets `scan`, `fix`, `verify`, `template`, `rules` and `component` all run with no network at all once the CLI is installed — the private-registry wall only bites on install, not on use.

| **3 — Move off @cdx** | `ng-add` for `@hlx`; `@cdx`→`@hlx` scope codemod + ng-update migrations per major; `helix migrate --to 22 --agent` | Pinned app reaches `@hlx` Helix 22 with leftovers tracked as TODOs |
| **4 — Extend** | `helix mcp` thin wrapper; scheduled snapshot dashboard over scan JSON; `helix export design-md` | Optional, driven by demand |

The first slice is `scan` plus `doctor` because adoption has not started, and a team cannot plan what it has not counted. It also fills the gap nobody else fills, works entirely on existing lint presets, and produces both the management metric and the agents' work queue at once. Primer and Salesforce show that a counter which can reach zero, combined with agents, finishes migrations in weeks rather than years. Templates, MCP and migrations all build on the scan output and the snapshot, and none of them is useful without it.

### Risks and how to contain them

The first risk is **metric gaming and disputed definitions**. Teams can rename classes or add disable comments to improve their numbers. Counting disables without a reason, publishing the coverage formula, and keeping heuristic template counts out of the headline figure limit this. The second is **rule duplication**. If `helix scan` grows its own rule engine, it will drift from the lint presets, so the SLDS pattern of wrapping ESLint should be treated as non-negotiable. The third is **unsafe autofix**. Colour substitution changes how things look. Fallbacks, confidence thresholds, dry-run as the default, and Canvas Kit's advice to keep codemod output in its own commit contain it ([Canvas Kit](https://canvas.workday.com/whats-new/upgrade-guides/canvas-kit-v8-upgrade-guide)). The fourth is **snapshot drift**. The CLI's data is a snapshot of the artifact, which is itself a generated view of the implementation; a package upgrade could move ahead of the snapshot. `helix doctor`'s reconciliation of the snapshot against the installed packages is the guard, and the CLI versioning in step with the Helix major keeps the two aligned by release. The fifth is **the private-registry wall for agents**, covered by skills that degrade gracefully, a documented read-only token, and a snapshot bundled in the package so the CLI needs no network once installed. The sixth is **Angular churn**. Helix tracks Angular majors, and the MCP surface Angular itself ships has changed five times in a year. Keeping logic in a versioned CLI and its JSON contract, with MCP as a replaceable wrapper, limits the exposure. The last risk is **thin evidence**. The Stripe account is secondhand, and no one has published data showing a CLI beats MCP for design-system output quality. Phase 2 should therefore include a small evaluation: the same chat-UI prompt run by several people with and without `helix template` and `verify`, scored by `helix scan`. That is Stripe's "three users, three outputs" test, run on Helix.

## Conclusion

Helix's position has changed. It is not behind peers on AI readiness. Its generated, no-drift definition of itself — tokens, a component manifest and a growing template catalog — plus its skills repo and sync command already match or exceed most enterprise systems' agent kits. What it lacks is a part no peer has built for Angular: a deterministic answer to "how Helix is this code, and did this change make it better?" Agents need that answer to stop producing Zombie UI, and managers need it to see adoption at all. The market's direction, from Stripe abandoning docs-only MCP to Angular and Nx trimming their tool surfaces, points to the same conclusion. The value lies in checks and scoped rules, not in more retrievable documentation, and not in a dependency on Figma or a third-party platform.

So the Helix CLI should mean **compliance as a command**. It should be small, private, built on JSON output, layered over the lint presets Helix already ships, fed by a snapshot of the Helix Angular definition, and called by public skills that treat `helix verify` as the definition of done. If the first slice delivers only `helix scan` with a baseline ratchet in the three consumer apps' CI, Helix will have something none of the surveyed Angular libraries offer: adoption that can be measured, can only go up, and that agents can work through on their own.
