# Make the Helix CLI the agent's verification loop

By 2026 the design-system tooling market has settled on a three-part shape. **Skills** carry the knowledge. A **lean MCP server**, where there is one, handles discovery. A **CLI** is the only thing that changes files or checks them. The Stripe story that made an impact is evidence for that shape, not a product to copy. Publicly, Stripe launched **Stripe Projects**, an agent-first CLI that provisions whole production stacks and has nothing to do with design systems. Internally, Stripe's design team **replaced an MCP server over its Sail docs with a custom CLI**, after the same prompt from three people produced three different interfaces. The CLI serves page templates, workflows and machine-readable rules in phases. Angular and Nx made the same move in 2026, cutting their MCP tool surfaces in favour of skills plus CLI and schematics. The basics are now table stakes: `--json`, non-interactive flags, dry-run, `setup --client`, `npx skills add`, lint presets with autofix and versioned codemods. What sets the leaders apart is a **validation loop** agents must close (Primer's `lint_css`, Shopify's component validator, Salesforce's SARIF-to-zero uplift) and an **agent hand-off for migration leftovers** (Ant Design, React Spectrum). The biggest gap is that **no adoption scanner works on Angular templates**: Omlet, react-scanner, Storybook's manifest on Webpack Angular and the shadcn registry are all React-first. For Helix, that gap is the opening. The Helix CLI should not become another component catalogue. It should be the one place that measures Helix adoption in Angular code, fixes the mechanical part, and gives agents a pass/fail check to work against. The first piece to build is `helix scan`, which turns the ~665 hard-coded colours and ~690 Material-internal overrides in the consumer apps into a baseline that CI enforces and agents can work down.

## Stripe's lesson was to swap MCP for a CLI, not to launch one

"Stripe launched a CLI" refers to two different things, and only one of them matters for Helix. The public launch was **Stripe Projects**. It went to developer preview on 26–27 March 2026 and reached GA at Stripe Sessions 2026 with 32 providers. It lets an agent provision hosting, databases, auth, analytics and AI services from the terminal, with credentials synced and billing in one place ([projects.dev](https://projects.dev/blog/production-ready-dev-stack-from-terminal/); [byteiota](https://byteiota.com/stripe-projects-ga-ai-agents-provision-dev-stack/)). It went from idea to preview in **seven weeks**. Stripe argued that the bottleneck for agents is not single API calls but the work around them: accounts, auth, credentials and billing ([projects.dev](https://projects.dev/blog/how-we-built-stripe-projects-in-seven-weeks/)). Around it, the Stripe CLI gained `stripe agent setup`. This command detects which coding agents you use and installs a plugin that configures Stripe's MCP server and installs skills that keep themselves up to date. Stripe also publishes a machine-readable skills index at `/.well-known/skills/index.json` for agents that cannot run `npx skills` ([Stripe docs](https://docs.stripe.com/skills.md)).

The design-system story is the one that matters for Helix. Stripe's Head of Design, Katie Dill, described it at the Lenny and Friends Summit (reported 10 September 2026). She named the problem **"Zombie UI"**: generic interfaces with no brand, produced by AI. Stripe first connected agents to Sail's documentation through an MCP server and found that **the same prompt from three users produced three different outputs**. It then built a **custom CLI on top of the design system** that serves complete page templates and workflows rather than single components. The CLI delivers documentation "at the right moment", in phases, to avoid context rot, and encodes strict design rules as machine-readable specs. Quality control moved to after the build, with an editorial review of finished interfaces ([Dr. Web](https://www.drweb.de/zombie-ui-stripe-design-system-ki/)). The evidence is thin. The only source is a German secondary article, no transcript was found, and Sail and its CLI are not public. The lesson is still clear, and the rest of the market backs it up: **giving agents access to documentation does not make them follow the brand**. What works is giving them templates, rules scoped to the task, and a checker.

Two Stripe patterns apply directly to Helix. The first is `stripe agent setup`: one command that detects the agent, installs skills and configuration, and keeps them updated. This is what `@cdx/helix-ai sync` already does in part. The second is the Sail CLI's progressive serving of templates and rules, which fits Helix's 19 single-source pattern guides, nine of them for AI interfaces. Those AI chat UIs have been rebuilt five times across consumer apps. That is the same "three users, three outputs" failure Stripe described.

## Every serious design system now ships skills, a thin MCP and a CLI that changes or checks files

Across about twenty systems surveyed, the same architecture keeps appearing. **shadcn** is the reference CLI for distributing components. Version 4.21.3 covers `init`, `add` (with `--dry-run`, `--diff` and `--view`), `search`, `view`, `docs --json`, `info --json`, `apply`, `migrate`, `eject`, `registry validate` and `mcp init --client`. It also ships an Agent Skill and an MCP server whose seven tools are all read-only. The install tool `get_add_command_for_items` *returns a CLI command for the agent to run* instead of writing files itself ([shadcn CLI](https://ui.shadcn.com/docs/cli); [shadcn MCP source](https://raw.githubusercontent.com/shadcn-ui/ui/main/packages/shadcn/src/mcp/index.ts)). At **~13.4M weekly downloads** it dwarfs every per-library CLI. Park UI's CLI, with ~4k a week and little activity, shows that standalone "add component" tools lose to shared formats ([npm API](https://api.npmjs.org/downloads/point/last-week/shadcn)). **Ant Design's `@ant-design/cli`** is the broadest single design-system binary found. It has offline `info`, `doc`, `demo`, `token` and `changelog` lookups, plus project commands `doctor`, `usage` and `lint`. Its `migrate <from> <to> --apply` command emits an "agent-ready migration prompt". `antd mcp` is built into the CLI, `setup --client` writes agent configuration, and everything supports `--format json` ([Ant Design: For Agents](https://ant.design/docs/react/for-agents)).

The enterprise systems split enforcement from knowledge. **Atlassian** has 83 ESLint rules, 30 of them autofixable, and tells teams not to maintain their own configuration. It runs codemods through `@atlaskit/codemod-cli`, with `--since-ref` and `--packages pkg@fromVersion`, and through Hypermod. Its `@atlaskit/ads-mcp` server includes axe-core accessibility analysis and **records tool-usage analytics with an opt-out** ([eslint plugin README](https://www.npmjs.com/package/@atlaskit/eslint-plugin-design-system); [codemod-cli](https://www.npmjs.com/package/@atlaskit/codemod-cli); [ads-mcp](https://www.npmjs.com/package/@atlaskit/ads-mcp)). **Salesforce** is the closest model to a single design-system CLI. `@salesforce-ux/slds-linter` offers `lint`, `lint --fix`, `report` (SARIF output) and `emit`, wraps its own ESLint plugin, and feeds an MCP tool, `orchestrate_lwc_slds2_uplift`, that works from the linter's output. Its `no-hardcoded-values-slds2` rule suggests the nearest styling hook by **CIEDE2000 ΔE** colour distance ([slds-linter](https://github.com/salesforce-ux/slds-linter); [eslint-plugin-slds](https://www.npmjs.com/package/@salesforce-ux/eslint-plugin-slds); [LWC MCP](https://developer.salesforce.com/docs/platform/lwc/guide/mcp-lwc.html)). **GitHub Primer's** MCP includes `lint_css`, which runs Stylelint with autofix on CSS the agent writes. Its instructions tell the agent the "task is incomplete without a success message" and include token bundles for each UI pattern to stop "property-by-property searching" (`@primer/mcp` v1.1.0 source; [primer.style MCP](https://primer.style/product/getting-started/foundations/mcp)). **Shopify** handled its Polaris React to web components move with agent skills and an MCP validator, `validate_component_codeblocks`, which rejects hallucinated components and props. It did not write new codemods, and its Stylelint and codemod packages have been frozen since March 2025 ([Shopify community](https://community.shopify.dev/t/speed-up-migrating-your-checkout-and-customer-account-ui-extensions-to-polaris-web-components-with-the-shopify-ai-toolkit/35092); [policylayer](https://policylayer.com/tools/dev/validate-component-codeblocks)).

The Angular ecosystem matters most for Helix, and its own platform owners point the same way. The Angular CLI's `ng mcp` server **dropped `find_examples` and `modernize` in April–May 2026** and folded build, test and e2e into one `run_target` tool. In place of a dedicated migration tool, agents now get "instructions for schematic discovery", so they find and run `ng update` migrations themselves ([angular-cli commits](https://github.com/angular/angular-cli/commits/main/packages/angular/cli/src/commands/mcp/tools)). Nx did the same in February 2026. `npx nx configure-ai-agents` writes AGENTS.md or CLAUDE.md plus skills for six agents, and the Nx MCP now defaults to `--minimal`, with workspace and generator tools hidden. Nx says MCP is "for connecting to remote services" ([Nx blog](https://nx.dev/blog/nx-ai-agent-skills); [Nx MCP reference](https://nx.dev/docs/reference/nx-mcp)). Among Angular component libraries, **Spartan** is the closest structural match to a Helix CLI. One package works as both an Angular schematic collection and an Nx plugin, has an `info --json` command that its own agent skill reads, and has a 17-tool MCP with health tools ([spartan.ng CLI](https://www.spartan.ng/documentation/cli); [skills](https://www.spartan.ng/documentation/skills)). **Kendo** moved major-version migrations out of `ng update` into `@progress/kendo-cli migrate`, a codemod CLI. Its MCP "Upgrade Assistant" runs the codemods, then uses AI to fix the remaining compile errors. Users have complained that the codemods reformat their HTML templates ([Telerik](https://www.telerik.com/kendo-angular-ui-develop/components/assisted-migration); [feedback 1696502](https://feedback.telerik.com/kendo-angular-ui/1696502-kendo-cli-migration-tool-option-to-suppress-automatic-reformatting-of-angular-html-templates)). **PrimeNG** ships a read-only MCP with `validate_usage` and `get_setup`, bundled with skills as a plugin ([primeng.dev/mcp](https://primeng.dev/mcp)).

## Table stakes are flags and installers; the edge is a gate agents must pass

The baseline is easy to state because almost everyone meets it. An agent-friendly CLI makes every input a flag and only prompts when a TTY is present. It supports `--json` or `--output json`, distinct non-zero exit codes for each failure type, `--non-interactive` or `--yes`, and `--dry-run`, and it leaves out spinners that waste context tokens ([Speakeasy](https://www.speakeasy.com/blog/engineering-agent-friendly-cli); [Layer5](https://layer5.io/blog/ai/design-for-the-human-enable-the-agent)). Each subcommand should document itself, so commands the agent is not using stay out of its context ([Vaughan](https://codex.danielvaughan.com/2026/04/28/building-agent-friendly-clis-codex-cli-composable-tool-design/)). On the knowledge side, the 2026 "AI-ready design system" kit has four parts: an `llms.txt` with a `.md` version of each page, installable Agent Skills through Vercel's `npx skills add` (which reaches 18+ agents), a one-line setup per client, and usually a docs MCP. Carbon, MUI, React Spectrum, PatternFly, Ant Design, Primer, Atlassian and Chakra all ship some version of it ([Vercel skills](https://vercel.com/changelog/introducing-skills-the-open-agent-skills-ecosystem); [React Spectrum AI](https://react-spectrum.adobe.com/ai); [Carbon MCP](https://carbondesignsystem.com/developing/carbon-mcp/onboarding-and-setup/)). On the code side, a recommended ESLint and Stylelint preset with autofix for token and deprecation rules is standard, as are versioned codemods that dry-run by default and need an explicit `--write` (Carbon, MUI, Canvas Kit, Paste, PatternFly) ([Carbon migration guide](https://carbondesignsystem.com/migrating/guide/develop); [MUI v7](https://mui.com/material-ui/migration/upgrade-to-v7/)). Helix already meets much of this baseline through helix-skills, the lint presets and `helix-ai sync`. What it lacks against peers is a `--json` contract, a `.well-known` skills index, and a single binary.

Four capabilities separate the leaders. The first is **validation the agent cannot skip**. Primer's `lint_css` gate, Shopify's anti-hallucination validator, PrimeNG's `validate_usage` and shadcn's `get_audit_checklist` all move design-system compliance from "the agent read the docs" to "the agent's output passed a check". This is the step Stripe's CLI encodes as rules. The second is **lint as a metric**. Polaris's `polaris/coverage` meta-rule groups violations into categories (color, space, typography, motion, and so on) and requires a stated reason for every disable comment, which makes opting out auditable ([stylelint-polaris](https://www.npmjs.com/package/@shopify/stylelint-polaris)). SLDS treats the SARIF violation count as the measure of progress, and zero means "uplifted" ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/salesforce-lightning-design-system-2-for-developers/transition-your-org-from-slds-1-to-slds-2)). The third is **an agent hand-off for whatever automation cannot finish**: Ant Design's `--apply` prompt, React Spectrum's `--agent` mode with a matching migration skill, and `TODO(S2-upgrade)` markers in code ([React Spectrum: Migrating](https://react-spectrum.adobe.com/migrating)). The fourth is **templates and rules served in phases rather than whole documents**, the Stripe pattern, which Primer's per-pattern token bundles come close to.

The impact data supports the last three. Primer tracked one countable anti-pattern, `sx` prop usage, from a peak of ~7,760 down to zero. An eight-engineer rotation migrated 6,419 over six months, then **two engineers with Copilot agents cleared the last 895 in three weeks** ([GitHub blog](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)). Salesforce Data Cloud uplifted thousands of custom components with **two engineers in one three-month release, against an estimated year or more of manual work**, using bulk autofix and SARIF triage ([Salesforce blog](https://www.salesforce.com/blog/data-cloud-slds-2-uplift/)). Atlassian's hex-to-token automation removed about **90% of the human work** in its dark-theme migration, and its codemod docs warn that results "will often not be perfect" ([Atlassian blog](https://www.atlassian.com/blog/announcements/the-story-of-dark-theme); [codemod-cli](https://www.npmjs.com/package/@atlaskit/codemod-cli)). The common recipe is a counter that can reach zero, automation for the mechanical bulk, and agents for the rest. No public evaluation shows that any design-system MCP improves output quality. The case for "CLI plus skills over MCP" rests on practitioner reports (Stripe, Angular, Nx), not on controlled data.

## Nobody measures design-system adoption in Angular templates

The clearest gap is measurement for anything other than React. **Omlet**, the leading adoption SaaS, scans React and React Native only, and Angular has been listed as "coming soon" without shipping ([npm @omlet/cli](https://www.npmjs.com/package/@omlet/cli)). **react-scanner**, the open-source scanner behind Elastic EUI's `eui-usage-analytics` and Brevo's adoption tracking, parses only JSX ([react-scanner](https://github.com/moroshko/react-scanner); [EUI usage analytics](https://github.com/elastic/eui/tree/main/packages/eui-usage-analytics); [Brevo](https://engineering.brevo.com/how-to-track-design-system-adoption/)). Ant Design's `antd usage` and Panda's `analyze` show that a usage report belongs inside the design-system CLI, but both are React or CSS-in-JS ([Panda CLI](https://panda-css.com/docs/references/cli)). The surrounding agent tooling is just as React-first. The Storybook MCP's docs toolset needs a component manifest that the Webpack-based `@storybook/angular` builder does not produce, only `@storybook/angular-vite` does ([Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview)). `storybook ai setup` supports React + Vite only. Figma's `get_design_context` emits React + Tailwind by default ([Figma MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). shadcn's registry, which v0 uses to pass "context from your design system to AI models", is a React distribution format ([v0 docs](https://v0.app/docs/design-systems)). An Angular and Material 3 team gets almost none of this out of the box.

Four further gaps follow. First, **nobody closes the loop as one agent-runnable sequence** of scan, structured violations, fix, and re-scan. SLDS comes closest, but it targets Salesforce's own LWC and Aura stack. Second, **drift between Figma and code is not covered end to end**. Terrazzo lints token quality and contrast, Figma's Code Connect tools show unmapped components, and Supernova sells "component health", but no first-party tool diffs Figma variables against code tokens for Angular ([Terrazzo linting](https://terrazzo.app/docs/linting/); [Supernova](https://www.supernova.io/blog/design-system-mcp-servers)). Third, **adoption has no agreed definition**. Practitioners report disagreement over what counts as a component and how to measure coverage ([guild.host](https://guild.host/presentations/measuring-the-unmeasurable-jucx6n)), and the alternatives range from import counts to pixel-based "visual coverage" ([guild.host](https://www.guild.host/presentations/measuring-design-systems-s7985q)). Fourth, **codemod platforms do not handle Angular templates well**. Codemod.com, Hypermod and GritQL are JavaScript and TypeScript first, with no confirmed support for Angular HTML templates ([Codemod](https://github.com/codemod/codemod); [Honeycomb/Grit](https://www.honeycomb.io/blog/honeycomb-acquires-grit)). The research also found nothing on how agents authenticate to a private npm registry from a sandbox, which matters directly for @cdx on Artifactory.

These gaps line up with Helix's situation. Adoption in the three consumer apps has not started. Their debt can be counted: ~665 hex colours, ~690 `.mat-mdc-*` and `::ng-deep` overrides, a version pin four majors behind, and loading, empty, error and chat states built by hand. Helix also already holds the pieces that peers lack: single-source pattern guides, lint presets, a checker, a sync command and a public skills repo. What is missing is the part that ties them together: **a measurement and verification command that understands Angular templates and SCSS**.

## A Helix CLI should measure, verify and hand off, in that order

### Positioning: one binary, built around compliance rather than a catalogue

The Helix CLI should be a single private package, **`@cdx/cli`, exposing a `helix` binary**. It should absorb `helix-check` (keeping it as an alias that calls `helix doctor`) and `@cdx/helix-ai sync` (which becomes `helix agent sync`). Its purpose in one sentence: *the Helix CLI tells a team or an agent how far an Angular app is from Helix, fixes the mechanical part, and gives a deterministic pass/fail check.* It should not try to compete with shadcn on distributing components. Helix ships npm packages, not copied source, and Panda's config-driven `analyze`/`check`/`--json` model fits a package-based system better than shadcn's "add" model ([Panda CLI](https://panda-css.com/docs/references/cli)). Nor should it be a second documentation site. Knowledge stays in the pattern guides and skills, and the CLI serves slices of it when asked. Following Salesforce, the CLI should **wrap the existing engines, not replace them**. `@cdx/eslint-config-helix`, using `@angular-eslint`'s template parser for HTML and TypeScript, and `@cdx/stylelint-config-helix` for SCSS stay the single rule catalogue, and `helix scan` runs them, combines the results and turns them into metrics. Rules then exist in one place, editors and CI show the same rule IDs, and the CLI adds categorisation, baselines, metrics and agent-ready output.

### Command surface

| Command | Purpose | Key flags | Precedent |
|---|---|---|---|
| `helix doctor` | Environment health (absorbs helix-check): Node, `.npmrc`/registry reachability, @cdx version skew vs Helix major, theme class, fonts, Storybook builder, agent config present | `--json`, `--fix`, `--offline` | Storybook `doctor`, Spartan healthcheck, `antd doctor` |
| `helix scan [path]` | Adoption + debt metrics over templates, TS, SCSS | `--format json\|sarif\|text`, `--baseline <file>`, `--fail-on regression\|any\|none`, `--category`, `--changed-since <ref>` | Polaris coverage, SLDS `report`, `antd usage` |
| `helix fix [category]` | Mechanical autofix (colour → token with fallback, deprecated imports, banned overrides where safe) | `--dry-run` (default), `--write`, `--min-confidence 0.8`, `--json` | SLDS `lint --fix` + ΔE, Carbon `--write` |
| `helix verify` | The agent gate: scan scoped to changed files + doctor, fails on any new violation | `--changed-since <ref>`, `--json` | Primer `lint_css`, shadcn audit checklist |
| `helix pattern list/get <name>` | Serve pattern guides in phases (overview → structure → states → a11y → checklist) | `--step`, `--json` | Stripe Sail CLI, Primer token bundles |
| `helix rules <file\|component>` | Rules relevant to *this* file's imports/selectors only | `--json` | Stripe phased rules |
| `helix component list/get <selector>` | Generated Angular manifest: selector, inputs/outputs, tokens, variants, examples, do/don't | `--json` | antd `info`, PatternFly JSON schemas |
| `helix migrate` | Orchestrate `ng update` per major, then scan, then emit leftover tasks | `--to 22`, `--step`, `--agent`, `--json` | Kendo migrate, Spectrum `--agent`, antd `--apply` |
| `helix agent setup/sync` | Detect agents, write skills + AGENTS.md/CLAUDE.md managed blocks + Copilot instructions (+ MCP later) | `--client claude\|copilot\|cursor\|codex`, `--check` | `stripe agent setup`, `nx configure-ai-agents`, Angular `ai-config` |
| `helix export design-md` | Emit DESIGN.md from @cdx tokens for Stitch/Claude Design | `--out` | Google DESIGN.md |
| `helix mcp` (Phase 4) | Thin stdio wrapper over the same `--json` commands | `--read-only` | `antd mcp` |

Every command follows one contract. Input comes only from flags, with prompts only when a TTY is present. Machine output goes to stdout and logs to stderr. Exit codes are fixed: **0** pass, **1** violations over threshold, **2** usage or config error, **3** environment failure (doctor), **4** regression against baseline. Commands never change files without `--write`. The scan report should be versioned and readable in both directions, by people and by agents:

### Agent-native design: skills and CLI first, MCP only as a thin wrapper

The evidence supports **skills plus a CLI as the main agent interface**, with MCP added later as a thin wrapper. Stripe left MCP-over-docs because output was inconsistent. Angular removed bespoke MCP tools in favour of agents discovering schematics. Nx hid generator tools behind `--no-minimal` and moved knowledge into skills. Angular's tool set changed about five times in 2026, which shows how unstable MCP tool surfaces still are ([angular-cli commits](https://github.com/angular/angular-cli/commits/main/packages/angular/cli/src/commands/mcp/tools); [Nx blog](https://nx.dev/blog/nx-ai-agent-skills)). The strongest argument for MCP points the other way. Primer, Shopify and PrimeNG get real value from *validation* tools, and some hosts, such as IDE Copilot setups, find MCP tools more easily than shell commands. Helix can have both by putting the logic in the CLI and, in Phase 4, exposing `helix mcp` with a handful of tools (`scan`, `verify`, `get_pattern`, `get_rules`, `get_component`) that call the same functions and return the same JSON. This follows the Ant Design model ([Ant Design MCP](https://ant.design/docs/react/mcp.md)). Docs-search tools are not worth building. That is the part Stripe found unreliable.

The skills in the public `uh-joan/helix-skills` repo should change from mainly reference material into **procedures that call the CLI**. Each skill should be 50–100 lines with explicit triggers, following Speakeasy's guidance. A new `helix-adoption` skill would run `helix scan --format json`, pick the highest-impact category, run `helix fix --dry-run` and then `--write` at a confidence threshold, handle what remains by hand using `helix rules <file>`, and **treat the task as unfinished until `helix verify` exits 0**. That last line is the same instruction Primer's MCP gives for `lint_css`. The existing `helix-patterns` skill should fetch `helix pattern get ai-chat --step structure` one step at a time instead of loading all 19 guides. That is the Stripe mechanism, and it directly targets the five rebuilt chat UIs. `helix agent setup` should **add to, not overwrite**, the files Angular's `ai-config` schematic and `nx configure-ai-agents` generate, keeping Helix content inside its managed block ([ai-config schema](https://raw.githubusercontent.com/angular/angular-cli/main/packages/schematics/angular/ai-config/schema.json)). Publishing `/.well-known/skills/index.json` on the Helix docs site, as Stripe and Nx do, lets agents fetch skills without `npx skills` ([Nx AI setup](https://nx.dev/docs/getting-started/ai-setup)).

### Adoption measurement for Angular templates

`helix scan` should parse templates with the Angular compiler, through `@angular-eslint/template-parser`, so it sees inline and external templates, structural control flow and attribute selectors exactly, rather than using regular expressions. It parses SCSS with the Stylelint and PostCSS stack. It should sort every UI element into four groups. **Helix** covers `cdx-*` and Helix directives. **Material-themed** covers `mat-*` under a Helix theme, which counts as compliant because Helix is Material 3. **Raw equivalents** are `<button>`, `<input>`, `<select>`, `<table>` and similar elements where a Helix or Material component exists. **Custom** covers app components. Coverage is then (Helix + Material-themed) ÷ (Helix + Material-themed + raw equivalents). Custom components are reported separately, because a custom component is not automatically a failure. Style debt follows Polaris's categories (color, space, typography, shape, motion, overrides) and counts hard-coded values, `.mat-mdc-*` selectors, `::ng-deep` and `!important`. **Disable comments without a stated reason count as debt**, using Polaris's `reportDescriptionlessDisables` approach. Pattern candidates for hand-rolled loading, empty, error and chat UIs come from heuristics, such as a spinner inside a conditional block with no `cdx` state component. They are labelled "candidates" with a confidence score and kept out of the headline coverage number, because heuristic counts are easy to dispute.

The most important design choice is the **baseline ratchet**. Nobody will fix 665 colours in one go, so `helix scan --baseline` stores per-file counts and `--fail-on regression` fails CI only when a count goes up. Every merged change can then only improve the numbers, and the trend becomes the adoption chart. This is Primer's burn-down to zero applied to every category, and it is the most useful thing the CLI can do for the three consumer apps. For organisation-wide dashboards, CI should upload the JSON as a build artifact that a scheduled job aggregates. This is the EUI approach without phoning home. Any telemetry from `helix agent` or `helix mcp` usage should follow Atlassian's opt-out design ([ads-mcp](https://www.npmjs.com/package/@atlaskit/ads-mcp)). Supernova already holds Helix tokens and exposes token-usage tools, so it can display the dashboard rather than the team building a new one ([Supernova](https://www.supernova.io/blog/design-system-mcp-servers)).

### Migration: schematics for version moves, lint autofix for debt, agents for what is left

Two different migration problems need two mechanisms. **Version moves**, such as @cdx 18.3 to 22, belong in **`ng update` schematics**. Fields in `package.json` (`schematics`, `ng-update.migrations`) make them discoverable by the Angular CLI, Nx (`nx migrate` runs Angular ng-update migrations) and the Angular MCP's schematic discovery, with nothing extra to install. `--create-commits` gives one commit per migration ([angular.dev schematics](https://angular.dev/tools/cli/schematics-for-libraries); [ng update](https://angular.dev/cli/update)). Helix should ship an `ng-add` in two phases, setting up dependencies, theme, fonts and AI configuration the way Material and Taiga do, plus one migration per major ([Material collection.json](https://raw.githubusercontent.com/angular/components/main/src/material/schematics/collection.json)). Material removes old migrations each major ([migration.json](https://raw.githubusercontent.com/angular/components/main/src/material/schematics/migration.json)), so the pinned app has to step through 19, 20, 21 and 22 on the matching @cdx versions. `helix migrate --to 22` should run those steps in order, run `helix scan` after each one, and stop at the first step that leaves the build broken. `ng update` has no documented `--dry-run`, so the orchestrator should insist on a clean git tree and use per-step commits as its rollback. **Style debt is not tied to an update moment.** It should live as lint rules with autofix and be applied through `helix fix`, using SLDS's ΔE nearest-token matching and its rule that replacements carry fallbacks (`var(--token, #hex)`), so visual changes stay reviewable ([eslint-plugin-slds](https://www.npmjs.com/package/@salesforce-ux/eslint-plugin-slds)). Edits must be surgical text replacements at the compiler's source positions, never re-printed templates, to avoid the reformatting complaint Kendo users raised. Whatever automation cannot do, such as replacing a hand-rolled empty state with the Helix pattern, becomes `TODO(helix-upgrade)` markers plus a JSON task list from `helix migrate --agent`, which the `helix-adoption` skill works through. Generic codemod platforms (Codemod.com, Hypermod) are not worth adopting until they handle Angular templates.

### Packaging and distribution across a private registry and a public skills repo

The split should be deliberate. **Executable logic and Helix-specific data are private. Instructions are public.** `@cdx/cli` ships from Artifactory and depends on nothing outside the @cdx scope and the Angular, ESLint and Stylelint toolchain the app already has. Its rule data, component manifest and pattern guides are generated at build time in cdx-next from the same `*.guide.md` sources that already feed docs, skills and Storybook, so the four outputs cannot drift. The CLI version moves in step with the Helix major so that `helix doctor` can compare a project against the Helix version it targets. The public helix-skills repo stays installable through `npx skills add uh-joan/helix-skills`, but every skill must handle **a missing CLI**. Agents in cloud sandboxes may not be able to reach repo.clarivate.io. When `helix` cannot be found, the skill should report the cause (`.npmrc` scope mapping or token) and fall back to guidance only, without guessing. This matters more than it looks. The research found no established pattern for agent access to private registries, so Helix should document a least-privilege, read-only Artifactory token for @cdx and treat it the way Stripe treats restricted API keys ([Stripe MCP](https://docs.stripe.com/mcp)). Generating a component manifest also makes it possible to move Helix Storybook to `@storybook/angular-vite`, which unlocks the Storybook MCP docs toolset for free.

### Phased roadmap

| Phase | Scope | Exit criterion |
|---|---|---|
| **0 — Measure (first slice, ~4 weeks)** | `@cdx/cli` with `helix doctor` (helix-check folded in, `--json`) and `helix scan` (templates + SCSS, JSON/SARIF, categories, baseline). Run on the three consumer apps; publish baselines. | Three committed `helix-baseline.json` files; numbers reproduce the ~665/~690 findings |
| **1 — Ratchet and fix** | `--fail-on regression` in consumer CI; `helix fix color` with ΔE + fallbacks; `helix verify`; `helix-adoption` skill | Colour/override counts trend down release-on-release with zero regressions |
| **2 — Guide the build** | `helix pattern`/`rules`/`component` from generated manifest; `helix agent setup` replaces `helix-ai sync`; `.well-known` skills index | Next AI chat UI built from `helix pattern get ai-chat` and passes `verify` without bespoke components |
| **3 — Move versions** | `ng-add` + ng-update migrations per major; `helix migrate --to 22 --agent` | Pinned app reaches @cdx 22 with leftovers tracked as TODOs |
| **4 — Extend** | `helix mcp` thin wrapper; Figma-variable/token drift via Supernova and Code Connect `.figma.ts` templates; `helix export design-md` | Optional, driven by demand |

The first slice is `scan` plus `doctor` because adoption has not started, and a team cannot plan what it has not counted. It also fills the gap nobody else fills, works entirely on existing lint presets, and produces both the management metric and the agents' work queue at once. Primer and Salesforce show that a counter which can reach zero, combined with agents, finishes migrations in weeks rather than years. Templates, MCP and migrations all build on the scan output, and none of them is useful without it.

### Risks and how to contain them

The first risk is **metric gaming and disputed definitions**. Teams can rename classes or add disable comments to improve their numbers. Counting disables without a reason, publishing the coverage formula, and keeping heuristic pattern counts out of the headline figure limit this. The second is **rule duplication**. If `helix scan` grows its own rule engine, it will drift from the lint presets, so the SLDS pattern of wrapping ESLint should be treated as non-negotiable. The third is **unsafe autofix**. Colour substitution changes how things look. Fallbacks, confidence thresholds, dry-run as the default, and Canvas Kit's advice to keep codemod output in its own commit contain it ([Canvas Kit](https://canvas.workday.com/whats-new/upgrade-guides/canvas-kit-v8-upgrade-guide)). The fourth is **the private-registry wall for agents**, covered by skills that degrade gracefully and a documented read-only token. The fifth is **Angular churn**. Helix tracks Angular majors, and the MCP surface Angular itself ships has changed five times in a year. Keeping logic in a versioned CLI and its JSON contract, with MCP as a replaceable wrapper, limits the exposure. The sixth is **thin evidence**. The Stripe account is secondhand, and no one has published data showing a CLI beats MCP for design-system output quality. Phase 2 should therefore include a small evaluation: the same chat-UI prompt run by several people with and without `helix pattern` and `verify`, scored by `helix scan`. That is Stripe's "three users, three outputs" test, run on Helix. The last risk is **maintenance load on a small team**. Shopify froze its tooling when its platform changed, so the CLI should stay narrow and avoid becoming a framework.

## Conclusion

Helix's position has changed. It is not behind peers on AI readiness. Its single-source guides, skills repo and sync command already match or exceed most enterprise systems' agent kits. What it lacks is a part no peer has built for Angular: a deterministic answer to "how Helix is this code, and did this change make it better?" Agents need that answer to stop producing Zombie UI, and managers need it to see adoption at all. The market's direction, from Stripe abandoning docs-only MCP to Angular and Nx trimming their tool surfaces, points to the same conclusion. The value lies in checks and scoped rules, not in more retrievable documentation.

So the Helix CLI should mean **compliance as a command**. It should be small, private, built on JSON output, layered over the lint presets Helix already ships, and called by public skills that treat `helix verify` as the definition of done. If the first slice delivers only `helix scan` with a baseline ratchet in the three consumer apps' CI, Helix will have something none of the surveyed Angular libraries offer: adoption that can be measured, can only go up, and that agents can work through on their own.
